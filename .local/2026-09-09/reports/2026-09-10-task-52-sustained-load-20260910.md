# Task 52 — sustained two-worker classroom load

## Status

**COMPLETE for the reusable package's local PostgreSQL acceptance contract.**

Two task-owned ASGI workers completed a 60-second warm-up and a 600-second
measured interval with two independent classrooms and 100 synthetic guest
participants in each. The run retained every acknowledged write, recovered
from a task-owned worker restart and WebSocket loss, and completed the separate
assessment autosave/restart/expiry/grading path while no assessment sockets
were present.

This is not host deployment or production capacity evidence. The task never
connected to xcWebServer or a non-loopback address, changed host resources, ran
migrations against a host database, or restarted a host service.

## Final implementation

Baseline was `f445002`; the final harness code is `e49602e` before this report
commit.

- `tests/acceptance/live_load.py` provides a loopback-only CLI and accepts
  `--base-url`, `--classrooms`, `--participants-per-class`,
  `--warmup-seconds`, `--duration-seconds`, interval, and relay-timeout
  settings. It rejects an occupied port, non-loopback URL, and non-loopback
  PostgreSQL host before it creates test data.
- `tests/test_multiworker_classroom.py` owns two Uvicorn workers, creates its
  synthetic data in the PostgreSQL pytest database, records each accepted
  idempotency key, and reconciles revisions after reconnect and restart.
- Long-running synthetic WebSocket clients now use an unbounded client receive
  queue. The previous default 16-message queue backpressured clients that were
  deliberately not rendering every state event, causing a server keepalive
  timeout during the ten-minute run. This is a harness-client correction; no
  production server keepalive setting changed.
- The harness now measures and enforces HTTP command p95 below 2 seconds and
  sampled post-notification WebSocket convergence p95 below 5 seconds.

## Environment and topology

- Shell: zsh; conda environment `django`; `/data/p/bin` first on `PATH`;
  `PYTHONPATH=.:src`.
- Python 3.12.5; PostgreSQL 17.11.
- Host: Intel Xeon Gold 5218R, 80 logical CPUs, 502 GiB memory (419 GiB
  available at preflight).
- Two task-owned loopback Uvicorn/Channels processes. Worker zero used
  `127.0.0.1:18529`; the second worker used an internally selected free
  loopback port. PostgreSQL relay was real, using the task-owned pytest
  database selected by the test harness.
- Synthetic workload: two classrooms × 100 guests, 200 live WebSockets,
  concurrent HTTP submissions and edits, teacher publish/settings/reveal,
  HTTP state refresh, a subset disconnect, one owned-worker restart and
  reconnect, and an explicit PostgreSQL notification per classroom.

`task52-final-duration-20260910`; it exited zero. Its durable artifacts are:

```zsh
python tests/acceptance/live_load.py \
  --base-url http://127.0.0.1:18529 \
  --classrooms 2 --participants-per-class 100 \
  --warmup-seconds 60 --duration-seconds 600 \
  --interval-seconds 2 --relay-timeout-seconds 45
```

Observed result:

```text

HTTP p50=801.7ms p95=1927.4ms max=6519.9ms;
```

The warm-up exceeded its requested minimum because each full 200-participant
write round completes before the interval boundary is checked. The measured
interval was 610.64 seconds. The expected accepted revision count was
`2 classrooms × 100 participants × (initial + edit + 5 warm-up + 54 measured)`
= 12,200, matching the durable reconciliation. The 200 retry responses were
idempotent replays, not additional revisions. The response p95 and relay p95
met the task's 2-second and 5-second budgets; the maximum HTTP time is reported
for diagnosis and was not the p95 acceptance threshold.

## Earlier failure and correction

The first full-duration attempt used the bounded default WebSocket receive
queue and failed after the measured interval with
`ConnectionClosedError: ... keepalive ping timeout`; its log remains at
`checks/task52-full-duration-20260910-142000/checks.log`. The accepted HTTP
writes and assessment scenario had already passed. The subsequent queue-fix
smoke run passed, then the final full-duration run above passed with explicit
relay timing. The defect, its cause, and its correction are retained here so
future load work does not mistake the failed attempt for a service regression.
